## ⚠️ 本書の扱いについて

本書に記載する保存場所・ファイル形式・コマンドは、**いずれのツールにおいても公開された安定 API ではなく内部実装である**。
公式ドキュメントと公開情報に基づく 2026-09 時点の調査結果であり、**予告なく変更されうる**（[requirements.md](./requirements.md) の R-1）。

したがって本書は次のように扱う。

1. 実装フェーズ（M0）で、**実際にインストールした各 CLI の実データに対して必ず再検証する**
2. 検証済みの実データをゴールデンファイルとして固定する（NFR-5.2）
3. アダプタは本書の内容をハードコードせず、**実データからの検出・フォールバック**を前提に実装する
4. 「要検証」と記した項目は、実装前に必ず現物で確認する

## 1. Claude Code

### 1.1 データルート

| OS | パス |
| --- | --- |
| macOS / Linux | `~/.claude` |
| Windows | `%USERPROFILE%\.claude` |

環境変数 `CLAUDE_CONFIG_DIR` が設定されている場合、本書の全 `~/.claude` パスがそのディレクトリ配下に移る。
**アダプタは必ず `CLAUDE_CONFIG_DIR` を優先すること**（FR-1.4）。

### 1.2 ディレクトリ構成

| パス | 内容 | Mochi での用途 |
| --- | --- | --- |
| `projects/<project>/<session-id>.jsonl` | セッションの完全なトランスクリプト（全メッセージ・ツール呼び出し・ツール結果） | **主データソース** |
| `projects/<project>/<session-id>/tool-results/` | 大きいツール出力を退避した別ファイル | FR-5.4 で参照解決 |
| `projects/<project>/<session-id>/subagents/` | サブエージェントのトランスクリプト | FR-5.7 |
| `projects/<project>/memory/` | プロジェクトの自動メモリ | 対象外（セッションではない） |
| `projects/<project>/<session>.orphaned-<ts>-<suffix>.jsonl` | 上書きせず退避された旧トランスクリプト | 既定で一覧非表示 |
| `projects/<project>/<session>.jsonl.superseded-<ts>` | 同上 | 既定で一覧非表示 |
| `sessions/` | **実行中セッションごとの小ファイル**（並行実行とクラッシュの検出用） | **FR-4.8（実行中判定）に利用** |
| `history.jsonl` | ユーザーが入力したプロンプトの履歴 | 補助（対象外でも可） |
| `~/.claude.json` | アプリ状態・プロジェクトごとの信頼設定・個人 MCP 設定 | 既知プロジェクト一覧の補助情報 |
| `shell-snapshots/`, `backups/`, `debug/`, `plans/`, `image-cache/`, `session-env/` | 内部用 | 対象外 |
| `todos/`, `statsig/`, `logs/` | 旧バージョンの遺物。現行では書かれない | 対象外 |

### 1.3 プロジェクトディレクトリ名 ★重要な落とし穴

`<project>` は **作業ディレクトリのパス区切りを `-` に置換したもの**である。

```
/Users/you/code/app   →   -Users-you-code-app
/home/user/work/my-repo → -home-user-work-my-repo
```

**この変換は非可逆である。** 元パスに `-` が含まれる場合（`my-repo` など）、
ディレクトリ名から元のパスを一意に復元することはできない。

> **実装要件**: セッションの cwd は**ディレクトリ名から逆算してはならない**。
> JSONL 各行に含まれる `cwd` フィールドから取得すること（[requirements.md](./requirements.md) FR-3.1 の注記）。

### 1.4 ファイル形式

JSONL（1 行 1 イベントの追記専用形式）。1 セッションが数日にまたがることがある（再開時は同一ファイルに追記される）。

各行に含まれると期待される情報（**要検証**、バージョン差あり）:

- イベント種別（ユーザーメッセージ / アシスタント応答 / ツール呼び出し / ツール結果 / 思考）
- セッション ID、イベント UUID、親 UUID（分岐の表現）
- タイムスタンプ
- `cwd`（作業ディレクトリ）
- git ブランチ、モデル名、Claude Code のバージョン
- ターンごとのトークン使用量

> 追記専用のため、**読み取り中に末尾行が不完全なことがある**（FR-2.6）。

### 1.5 保持期間 ★要注意

トランスクリプトは設定 `cleanupPeriodDays`（**既定 30 日**、最小 1）に基づき自動削除される。
`desktopSessionCleanupPeriodDays` は Claude Desktop / Cowork のトランスクリプトに適用される別設定。

> **実装要件**: Mochi は元ファイル消失後もインデックス内の本文を保持し、
> 「元ファイルなし（アーカイブ済み）」として閲覧可能にする（FR-2.11）。これは Mochi の主要な価値の 1 つになる。

### 1.6 セッション再開コマンド

```
claude --resume <session-id>     # ID 指定で再開
claude -c                        # 直近セッションの継続
```

起動時の cwd は、セッションの `cwd` に合わせる（FR-7.1）。

### 1.7 実装上の注意

- `sessions/` 配下の実行中セッションファイルにより、実行中判定ができる（FR-4.8）
- トランスクリプトは暗号化されていない。`.env` を読んだ・認証情報を出力したツール結果はそのまま `projects/<project>/<session>.jsonl` に書かれる → NFR-3.3 のマスキングが必須
- 退避ファイル（`.orphaned-*`, `.superseded-*`）は一覧をノイズで埋めるため既定非表示とし、設定で表示可能にする

## 2. OpenAI Codex CLI

### 2.1 データルート

| OS | パス |
| --- | --- |
| macOS / Linux | `~/.codex` |
| Windows | `%USERPROFILE%\.codex` |

環境変数 `CODEX_HOME` があればそれを優先する（**要検証**）。

### 2.2 ディレクトリ構成

| パス | 内容 | Mochi での用途 |
| --- | --- | --- |
| `sessions/YYYY/MM/DD/rollout-<ISO8601>-<uuid>.jsonl` | セッションの rollout ファイル。会話・ツール呼び出し・その出力の完全な記録 | **主データソース** |
| `history.jsonl` | プロンプト履歴 | 補助 |
| `config.toml` | Codex CLI の設定 | 読み取り専用の参照のみ |
| アーカイブ済みセッションの格納先 | 新しめのバージョンにセッションのアーカイブ機能がある | **要検証** — アーカイブ済みも一覧対象にするか要判断 |

セッションファイルが**日付でディレクトリ階層化されている**点が他 2 ツールと異なる。
スキャン時は `sessions/**/rollout-*.jsonl` を再帰探索する。

### 2.3 ファイル形式

JSONL。**先頭行にセッションのメタ情報**が入る（`SessionMeta`）。含まれると期待される項目（**要検証**）:

- セッション ID（UUID）
- `cwd`（作業ディレクトリ）
- CLI バージョン
- 起動元（originator）
- instructions（システム指示）
- タイムスタンプ

以降の行が会話とツール実行のイベント列。**リプレイ可能な完全な状態記録**として設計されている。
再開時は新規ファイルを作らず**同じ rollout ファイルに追記**される。

### 2.4 セッション ID の取得 ★重要

ファイル名（`rollout-<timestamp>-<uuid>.jsonl`）にも UUID が含まれるが、
**ファイルはユーザーが任意にリネームでき、`resume` が参照するのは JSONL 内部に記録されたセッション ID である。**

> **実装要件**: 再開に使う ID は**ファイル名からではなく先頭行のメタ情報から取得する**
> （[requirements.md](./requirements.md) R-8）。

### 2.5 セッション再開コマンド

```
codex resume <session-id>    # ID 指定
codex resume --last          # 直近セッション
codex resume                 # 対話的なピッカー
```

Mochi からは ID 指定形式を使う。ピッカー形式は使わない。

### 2.6 実装上の注意

- 日付階層のため、増分スキャンは「直近 N 日のディレクトリのみ」に最適化できる
- ファイル監視は `sessions/` 配下の再帰監視が必要（新しい日付ディレクトリが動的に作られる）
- バージョンにより archive / fork / compact といったセッション操作が追加されている。fork されたセッションの親子関係を表示できるとよい（**要検証**、v0.2 候補）

## 3. OpenCode

### 3.1 データルート

| OS | パス |
| --- | --- |
| macOS / Linux | `~/.local/share/opencode` |
| Windows | `%USERPROFILE%\.local\share\opencode` |

**Windows でも `~/.local/share` 配下を使う**（`%APPDATA%` ではない）点に注意。
`XDG_DATA_HOME` が設定されていればそれに従う（**要検証**）。

### 3.2 ストレージ形式がバージョンで異なる ★最大の注意点

OpenCode はストレージ実装が変遷しており、**インストール済みバージョンによって構造が異なる**。

**旧形式（JSON ファイル）**

| パス | 内容 |
| --- | --- |
| `storage/session/` | セッションのインデックス／メタ情報 JSON |
| `storage/message/<sessionID>/` | メッセージ本体 |
| `storage/part/` | メッセージのパート・ファイル内容のスナップショット |
| `storage/session_diff/` | セッションの差分 |

**新形式（SQLite）**

| パス | 内容 |
| --- | --- |
| `opencode.db` | セッション・メッセージを格納する SQLite DB |
| `project/<project-id>/` | プロジェクト単位のデータ |

**共通**

| パス | 内容 |
| --- | --- |
| `auth.json` | プロバイダの認証情報 — **絶対に読み取らない／表示しない** |
| `log/` | アプリケーションログ |
| `worktree/` | OpenCode 自身が作成した git worktree |

### 3.3 推奨する連携方式: ローカル HTTP API を第一情報源にする ★

OpenCode は**サーバーモードと公開 API を持つ**。

```
opencode serve        # HTTP サーバを起動
```

- OpenAPI 3.1 仕様を公開しており、そこから TypeScript SDK が生成されている
- `GET /session`（セッション一覧）をはじめとするセッション CRUD、`GET /session/status` 等を提供する

> **実装方針**: ストレージ形式の変動が激しいため、**API を第一の情報源とし、ファイル直読みをフォールバックにする**
> 二段構えのアダプタとする（[requirements.md](./requirements.md) 7.2）。
> API はドキュメント化された安定インタフェースであり、内部ストレージ実装より変更耐性が高い。

考慮点:

- サーバが起動していない場合の扱い（Mochi が必要時に起動するか／ファイル読みに落とすか）を設計で決める
- API はローカルバインドであることを確認し、外部公開しない（NFR-3.1）
- API のポート・認証方式を**要検証**

### 3.4 プロジェクト（リポジトリ）との対応

OpenCode はセッションを **project 単位**で持つ（`project-id`）。
この project がどのように git リポジトリと対応づけられるかを**要検証**。
対応が取れない場合は、セッションの cwd から Mochi 側で解決する（FR-3.1）。

### 3.5 セッション再開コマンド

```
opencode --session <id>     # 要検証
```

正確なフラグ名・形式は実装前に `opencode --help` で**必ず確認する**。
API 経由でセッションを開く手段があればそちらも検討する。

### 3.6 実装上の注意

- OpenCode デスクトップ版はさらに別の状態ファイル（Windows: `%APPDATA%\ai.opencode.desktop\` 配下等）を持つ。**MVP では TUI/CLI のセッションのみを対象とする**
- SQLite DB を読む場合は**読み取り専用モードで開き**、OpenCode 本体の書き込みをブロックしないこと（WAL モードの考慮を含む）
- セッションが自動削除されないためストレージが単調増加する。ディスク使用量の可視化（FR-8.2）の価値が特に高い

## 4. 3 ツール比較サマリ

| 観点 | Claude Code | Codex CLI | OpenCode |
| --- | --- | --- | --- |
| データルート | `~/.claude`（`CLAUDE_CONFIG_DIR`） | `~/.codex`（`CODEX_HOME`） | `~/.local/share/opencode`（Windows も同じ） |
| 主形式 | JSONL | JSONL | JSON ファイル群 または SQLite（バージョン依存） |
| ディレクトリ構造 | cwd 由来のプロジェクト名 | 日付階層 | project ID 単位 |
| 1 セッション = 1 ファイル | ✅ | ✅ | ❌（分割 or DB） |
| 再開時の挙動 | 同一ファイルに追記 | 同一ファイルに追記 | 要検証 |
| cwd の取得元 | JSONL 内 `cwd` フィールド（ディレクトリ名からは復元不可） | 先頭行のメタ情報 | API または DB（要検証） |
| セッション ID の取得元 | ファイル名（= session-id）※内容とも一致 | **JSONL 内部**（ファイル名は当てにしない） | API または DB |
| 実行中判定の手段 | `~/.claude/sessions/` の実行中ファイル | 要検証 | API（`/session/status` 等） |
| 自動削除 | ✅ 既定 30 日（`cleanupPeriodDays`） | 要検証 | ❌ 自動削除なし |
| 公開 API | なし | なし（app-server の JSON-RPC あり／要検証） | ✅ HTTP + OpenAPI + SDK |
| 推奨アクセス方式 | ファイル読み取り | ファイル読み取り | **HTTP API 優先**、ファイルはフォールバック |

## 5. M0（調査・PoC）フェーズで確定すべきこと

実装前に、実際の CLI をインストールして次を必ず確認する。

- [ ] 3 ツールそれぞれの最新版と、少なくとも 1 つ前のメジャー／マイナー版でのセッションファイルを採取する
- [ ] 各 JSONL の全イベント種別と、必須／任意フィールドの一覧を確定する
- [ ] Windows と macOS の両方でパスを実測する（環境変数オーバーライドの挙動を含む）
- [ ] Codex のアーカイブ済みセッションの格納先と、アーカイブ／fork の表現方法
- [ ] OpenCode の HTTP API のポート・認証・`GET /session` のレスポンススキーマ
- [ ] OpenCode の新旧ストレージ形式の判定方法（バージョン検出 or ファイル存在判定）
- [ ] 各ツールの正確な再開コマンド（`--help` の実出力）と、cwd の指定方法
- [ ] 各ツールの実行中セッション判定手段
- [ ] 日本語パス・空白入りパス・長いパスでの各ツールの挙動
- [ ] 採取したファイルをゴールデンファイルとしてリポジトリに固定する（**シークレットを完全に除去した上で**）
