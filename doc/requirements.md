## 1. 背景と目的

### 1.1 背景

開発者は現在、複数のコーディングエージェント CLI を並行して使い分けている。

- **OpenAI Codex CLI**
- **Claude Code**
- **OpenCode**

これらはいずれも「セッション（会話履歴＋ツール実行履歴）」をローカルディスクに永続化するが、
**保存場所・ディレクトリ構造・ファイル形式・セッション ID 体系がツールごとに完全にバラバラ**である。
その結果、次の課題が生じている。

| # | 課題 |
| --- | --- |
| P-1 | 「どのリポジトリで、いつ、どのツールで、何を作業したか」を横断的に把握できない |
| P-2 | 過去セッションの再開に、ツール固有のコマンドと ID を思い出す必要がある |
| P-3 | 「あのエラーの解決方法をどこかのセッションで見た」が検索できない（ツールをまたいだ全文検索手段がない） |
| P-4 | セッションログがディスクを圧迫するが、何がどれだけ使っているか可視化されていない |
| P-5 | ツールによっては保持期間を過ぎたセッションが自動削除され、気づかないうちに履歴を失う |
| P-6 | 1 つのリポジトリに対して複数ツールを使った場合、作業の連続性が失われる |

### 1.2 目的

本アプリケーション **Mochi** は、ローカル PC 上に散在する上記 3 ツールのセッションを
**リポジトリ単位で集約・閲覧・検索・再開**できるデスクトップアプリケーションを提供する。

### 1.3 プロダクトゴール

- **G-1**: ユーザーが「リポジトリ」を起点に、ツールを問わず全セッションを一覧できる
- **G-2**: 任意のセッションを 2 クリック以内で、正しい作業ディレクトリ・正しいコマンドで再開できる
- **G-3**: 全ツール・全リポジトリを横断した全文検索ができる
- **G-4**: ユーザーのソースコードと会話ログを外部に一切送信しない（完全ローカル動作）

## 2. スコープ

### 2.1 対象ツール

| ツール | 対象 | 備考 |
| --- | --- | --- |
| OpenAI Codex CLI | ✅ MVP | `~/.codex/sessions/**/rollout-*.jsonl` |
| Claude Code | ✅ MVP | `~/.claude/projects/<project>/<session>.jsonl` |
| OpenCode | ✅ MVP | ローカル HTTP API 優先＋ファイル直読みフォールバック |
| その他（Aider, Cursor CLI 等） | ❌ 対象外 | アダプタ機構により将来追加可能な設計にする |

### 2.2 対象 OS

| OS | 対象 | 要件 |
| --- | --- | --- |
| Windows | ✅ | Windows 11（x64 / arm64）。Windows 10 22H2 はベストエフォート |
| macOS | ✅ | macOS 13 Ventura 以降（Apple Silicon / Intel） |
| Linux | ⚠️ | **v1 では非対象**（動作保証もビルド提供もしない）。ただし需要次第で追加しうるため排除はしない（Q-6）: OS 依存処理は抽象化し、OSS 化（NFR-4b）に伴うコミュニティからの追加を妨げない設計とする。なお OpenCode は 3 OS とも `~/.local/share/opencode` を使うため、同アダプタは事実上そのまま動く見込み |

### 2.3 リリーススコープ

#### MVP（v0.1）— 「読む・探す・動かす」

- セッションの自動検出とインデックス化（3 ツール）
- リポジトリ単位のグルーピングと一覧
- セッション一覧・詳細（トランスクリプト）ビューア
- 横断全文検索
- 対応 CLI でのセッション再開（**内蔵ターミナル**および外部ターミナル）
- **内蔵ターミナルでのセッション実行とライブ表示**（Q-1）
- タグ／ピン／メモによる整理
- **セッションの削除**（安全策つき、Q-2）

#### v0.2 以降（バックログ）

- トークン／コスト集計ダッシュボード
- Markdown / JSON エクスポート
- git worktree との連携表示
- セッションの棚卸し支援（期間・リポジトリを指定した一括削除、FR-8.6）

### 2.4 非スコープ（明示的に作らないもの）

- **NS-1**: エージェント機能そのものの実装（LLM API を直接呼ばない）
- **NS-2**: 各 CLI のインストール・アップデート管理
- **NS-3**: クラウド同期、チーム共有、Web 版
- **NS-4**: 各 CLI の設定ファイル（`config.toml`, `settings.json` 等）の GUI 編集
- **NS-5**: セッションログのクラウドバックアップ
- **NS-6**: UI の多言語化（i18n）。表示言語は英語のみとする — NFR-6.4 のデータ取り扱いとは別
- **NS-7**: サードパーティ製アダプタのためのプラグイン API 公開。**対象は 3 ツール固定**とする（Q-4）。アダプタ分離は内部設計にとどめる（NFR-5.1）

## 3. 想定ユーザーとユースケース

### 3.1 ペルソナ

**P-A: マルチツール開発者（主ターゲット）**
複数リポジトリを並行して触り、タスクの性質でツールを使い分ける個人開発者／小規模チーム所属エンジニア。
1 日に 5〜20 セッション、数か月で数千セッションが蓄積される。

**P-B: 履歴を資産として使う開発者**
過去の試行錯誤（うまくいかなかった方法を含む）を検索して再利用したい。

### 3.2 主要ユースケース

| ID | ユースケース | 受け入れシナリオ |
| --- | --- | --- |
| UC-01 | 作業の再開 | リポジトリ `foo` を選び、直近の Claude Code セッションを選択して「再開」。正しい cwd で `claude --resume <id>` が起動する |
| UC-02 | 横断検索 | 「`ECONNRESET`」で全文検索し、3 か月前の Codex セッションのヒット箇所にジャンプする |
| UC-03 | リポジトリ別の棚卸し | リポジトリごとのセッション数・ディスク使用量を確認し、不要なものを削除する |
| UC-04 | ツール比較 | 同一リポジトリの同一タスクについて、Codex と Claude Code のセッションを並べて確認する |
| UC-05 | 進行中セッションの把握 | 今どのリポジトリでどのツールが動いているかを一覧する |
| UC-06 | 新規セッション開始 | Mochi 上でリポジトリとツールを選び、新しいセッションを起動する |
| UC-07 | 履歴の共有 | セッションを Markdown にエクスポートし、シークレットをマスクした上で同僚に渡す |

## 4. 機能要件

優先度: **[M]** = MVP 必須 / **[S]** = MVP で望ましい / **[C]** = v0.2 以降

### FR-1. ツール検出と設定

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-1.1 | M | インストール済みの対象 CLI を自動検出する（`PATH` 探索、および OS ごとの既定インストール先の探索） |
| FR-1.2 | M | 検出した CLI のバージョンを取得し表示する（`--version` 実行） |
| FR-1.3 | M | CLI 実行ファイルのパスをユーザーが手動で上書きできる |
| FR-1.4 | M | 各ツールのデータディレクトリを手動で上書きできる（環境変数 `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_DATA_HOME` 等を優先的に尊重する） |
| FR-1.5 | M | ツールごとに有効／無効を切り替えられる（未インストールのツールは自動的に無効表示） |
| FR-1.6 | S | 検出に失敗した場合、原因（未インストール／パス不正／権限不足）を区別して表示する |

### FR-2. セッションの探索とインデックス化

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-2.1 | M | 各ツールのセッションストアをスキャンし、セッションを列挙する |
| FR-2.2 | M | スキャン結果をローカルの正規化インデックス（SQLite）に格納する |
| FR-2.3 | M | 再スキャンは増分で行う（ファイルの mtime / size / inode で変更判定し、未変更ファイルは再パースしない） |
| FR-2.4 | M | セッションストアをファイル監視し、新規セッション・更新を準リアルタイム（10 秒以内）に反映する |
| FR-2.5 | M | **元のセッションファイルは既定で読み取り専用として扱う。** 書き込み・改変は行わない（FR-7.3 の明示的削除操作を除く） |
| FR-2.6 | M | 追記中のファイル（末尾行が不完全な JSONL）を安全に扱い、壊れた末尾行はスキップして残りを表示する |
| FR-2.7 | M | パース不能なセッションはエラーとして隔離し、そのセッションのみ「読み取り失敗」と表示する。アプリ全体や他セッションの表示を阻害しない |
| FR-2.8 | M | 未知のフィールド・未知のイベント種別が現れても落ちず、生 JSON として表示可能なフォールバックを持つ |
| FR-2.9 | M | 初回フルインデックスはバックグラウンドで実行し、進捗（件数／推定残り時間）を表示する。実行中も既にインデックス済みの範囲は閲覧できる |
| FR-2.10 | S | インデックスの手動再構築（フルリスキャン）ができる |
| FR-2.11 | S | **トランスクリプトの元ファイルが削除された**セッションを検出し、状態 **`archived`（表示名: Archived）** として区別表示する。パース済みの本文はインデックスに保持し引き続き閲覧できる（P-5 対策）。この状態は再開できない |
| FR-2.12 | S | スキャン対象ディレクトリの追加・除外パターンを設定できる |

### FR-3. リポジトリ単位の管理 ★中核機能

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-3.1 | M | 各セッションの作業ディレクトリ（cwd）から、所属する git リポジトリのルートを解決する |
| FR-3.2 | M | git worktree（`.git` がファイルのケース）を正しく解決し、共通リポジトリに紐づける |
| FR-3.3 | M | リポジトリの同一性を以下の順で判定する: ① 初回コミットハッシュ ② `origin` のリモート URL（正規化: scheme/認証情報/末尾 `.git` を除去） ③ 正規化済み絶対パス。これによりディレクトリ移動後や複数クローンでも同一リポジトリとして束ねられる |
| FR-3.4 | M | worktree・複数クローンを「同一リポジトリとして束ねる／別として扱う」をユーザーが設定で選べる |
| FR-3.5 | M | パスの正規化を行う。少なくとも次を吸収する: Windows のドライブレター大小文字、パス区切り（`\` / `/`）、macOS の `/var` → `/private/var` 等のシンボリックリンク、大文字小文字を区別しないファイルシステム、末尾スラッシュ |
| FR-3.6 | M | cwd が git リポジトリでない、または既に存在しないセッションは「リポジトリ未所属」グループにまとめる。パスが存在しないことを明示する |
| FR-3.7 | M | リポジトリ一覧に次を表示する: 表示名、絶対パス、リモート URL、最終セッション日時、ツール別セッション数、合計セッション数 |
| FR-3.8 | S | リポジトリ一覧に、集計したトークン数・推定コスト・ディスク使用量を表示する |
| FR-3.9 | S | セッションのリポジトリ紐付けを手動で修正できる。リポジトリの手動マージ・分割ができる |
| FR-3.10 | S | リポジトリに表示名（エイリアス）・色ラベルを設定できる |
| FR-3.11 | S | 特定のリポジトリを一覧から非表示（除外）にできる |
| FR-3.12 | C | リポジトリの現在の git 状態（ブランチ、dirty か、worktree 一覧）を表示する |

> **重要な設計上の注意**
> Claude Code のプロジェクトディレクトリ名は cwd のパス区切りを `-` に置換したもの（例: `/Users/you/code/app` → `-Users-you-code-app`）だが、
> **元パスに `-` が含まれる場合この変換は非可逆**である。cwd はディレクトリ名から復元してはならず、
> **必ず JSONL 各行の `cwd` フィールドから取得する**こと。詳細は [tool-integration.md](./tool-integration.md) を参照。

### FR-4. セッション一覧

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-4.1 | M | 選択中のリポジトリに属するセッションを一覧表示する。「全リポジトリ」表示も可能 |
| FR-4.2 | M | 一覧に次を表示する: ツール種別（アイコン）、タイトル、開始日時、最終更新日時、メッセージ数、状態（実行中／終了／読み取り失敗／元ファイルなし） |
| FR-4.3 | M | タイトルは最初のユーザープロンプトの先頭から自動生成する（ツールがタイトルを保持している場合はそれを優先） |
| FR-4.4 | M | 並べ替え: 最終更新日時（既定・降順）、開始日時、メッセージ数、サイズ |
| FR-4.5 | M | 絞り込み: ツール、期間、状態 |
| FR-4.6 | S | 絞り込み: モデル名、git ブランチ、タグ、ピン留め |
| FR-4.7 | S | 使用モデル、入出力トークン数、推定コスト（FR-10.6）、git ブランチ、ファイルサイズを表示する |
| FR-4.8 | S | 実行中セッションをリアルタイムに識別して先頭に表示する（UC-05） |
| FR-4.9 | M | 1 万件規模のセッションでも仮想スクロールにより滑らかに操作できる |

### FR-5. セッション詳細（トランスクリプトビューア）

| FR-5.3 | M | ツール呼び出しの入力（引数）と出力を構造化表示する。既定で折りたたみ、クリックで展開 |
| FR-5.4 | M | 巨大なツール出力は遅延読み込みし、UI をブロックしない。別ファイルに退避された出力（Claude Code の `tool-results/`）も辿って表示する |
| FR-5.5 | M | セッション内検索（ハイライト＋前後移動） |
| FR-5.6 | S | ファイル差分（diff）を色付きで表示する |
| FR-5.7 | S | サブエージェントのトランスクリプトを親セッションから辿れる（Claude Code の `subagents/`） |
| FR-5.8 | S | 元の生 JSONL を「生データ表示」で確認できる |
| FR-5.9 | S | セッションのメタ情報パネル（ID、ツール、バージョン、モデル、cwd、ブランチ、ファイルパス、サイズ、トークン内訳） |
| FR-5.10 | S | ファイルパスをクリックしてエディタ（VS Code 等）で開ける |

### FR-6. 横断検索

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-6.1 | M | 全セッションの本文を対象とした全文検索を提供する |
| FR-6.2 | M | 検索スコープを切り替えられる: 全体／特定リポジトリ／特定セッション |
| FR-6.3 | M | 検索結果にツール名・リポジトリ名・日時・該当箇所のスニペット（ハイライト付き）を表示し、クリックで該当箇所にジャンプする |
| FR-6.4 | M | 検索とフィルタ（ツール／期間／リポジトリ）を併用できる |

| FR-6.6 | S | AND / OR / フレーズ（引用符）検索 |
| FR-6.7 | C | 正規表現検索 |

### FR-7. セッションの起動・再開・管理

| ID | 優先 | 要件 |
| --- | --- | --- |
| FR-7.1 | M | 選択したセッションを、対応する CLI で再開する。**必ずそのセッションの cwd をカレントディレクトリとして起動する** |
| FR-7.2 | M | ツールごとの正しい再開コマンドを組み立てる（例: `claude --resume <id>` / `codex resume <id>` / OpenCode の該当手段）。コマンドの正確な形は各 CLI のバージョンに追従して検証すること |
| FR-7.3 | M | 起動に使うターミナルを選択できる。Windows: Windows Terminal / PowerShell / cmd、macOS: Terminal.app / iTerm2 / その他任意のアプリ。「その他」としてコマンドテンプレートを自由設定できる |
| FR-7.4 | M | 再開コマンドをクリップボードにコピーできる（自動起動を使わないユーザー向け） |
| FR-7.5 | M | コマンド組み立て時に引数を OS ごとに正しくエスケープする。空白・日本語・記号を含むパスで破綻しないこと。**ユーザー入力・セッションデータをシェルに未エスケープで渡してはならない** |
| FR-7.6 | M | **セッションの cwd が存在しない**場合は起動を試みず、状態 **`cwd_missing`（表示名: Working directory missing）** として明示する。トランスクリプトの閲覧は引き続き可能 |
| FR-7.6a | S | `cwd_missing` のセッションに対し、新しいディレクトリを指定して cwd を付け替える（Relocate）操作を提供する。付け替えは Mochi 側 DB にのみ記録し、元ファイルは改変しない |
| FR-7.7 | S | 任意のリポジトリ × 任意のツールで新規セッションを開始する（UC-06） |
| FR-7.8 | **M** | **内蔵ターミナル**でセッションを実行し、出力を Mochi 上でライブ表示する（Q-1 で MVP 採用）。PTY を用いる（Windows: ConPTY、macOS: forkpty） |
| FR-7.8a | M | 再開（FR-7.1）と新規開始（FR-7.7）の実行先を「内蔵ターミナル」「外部ターミナル」から選べる。既定は内蔵。外部起動（FR-7.3）は残す |
| FR-7.8b | M | 内蔵ターミナルは複数同時に開ける。セッションごとにタブを持ち、リポジトリ名とツール名で識別できる |
| FR-7.8c | M | 入力を受け付ける（対話型 CLI であるため必須）。リサイズ時に PTY へウィンドウサイズ変更を伝える |
| FR-7.8d | M | スクロールバックの行数上限を設ける。上限超過時は古い行から破棄する（NFR-1.7 のメモリ目標を守るため） |
| FR-7.8e | M | 内蔵ターミナルで実行中のセッションは、Mochi が直接プロセスを把握できる。これを実行中表示（FR-4.8）の第一の情報源とし、ファイル監視による推定はフォールバックとする |
| FR-7.8f | M | アプリ終了時に実行中のプロセスがある場合は確認を求める。ユーザーの選択なしにエージェントの作業を打ち切らない |
| FR-7.8g | S | 内蔵ターミナルで進行中のセッションのトランスクリプトを、追記に追従して右ペインに反映する |

## 6. データモデル（論理）

Mochi は各ツールの生データを、以下の共通スキーマへ正規化してインデックスする。

```
Repository
  id                 (内部ID)
  display_name       表示名（ユーザー変更可）
  root_path          正規化済み絶対パス
  remote_url         正規化済み origin URL（任意）
  root_commit        初回コミットハッシュ（任意、同一性判定用）
  is_worktree        worktree か
  parent_repo_id     worktree の場合の親
  hidden             一覧から除外するか
  color_label

Session
  id                 (内部ID)
  tool               codex | claude_code | opencode
  native_id          ツール固有のセッションID（再開に使う）
  repo_id            → Repository（NULL 可 = リポジトリ未所属）
  cwd                セッションの作業ディレクトリ（生値）
  git_branch         記録されていれば
  title              生成 or 取得したタイトル
  model              主に使われたモデル
  started_at / updated_at
  message_count
  tokens_in / tokens_out / cost_estimate
  status             running | finished | unknown
  source_path        元ファイルの絶対パス
  source_size / source_mtime / source_hash   増分判定用
  schema_version     検出した形式バージョン
  parse_status       ok | partial | failed | archived      ← 元ファイルが消えた（FR-2.11）
  cwd_exists         bool  ← false なら cwd_missing（FR-7.6）。parse_status とは独立
  parse_error

Message
  id / session_id / seq
  role               user | assistant | tool_call | tool_result | system | thinking
  content            本文（テキスト化したもの）
  raw                元 JSON（フォールバック表示用）
  timestamp
  parent_id          分岐・サブエージェント用
  tokens_in / tokens_out

Annotation            （Mochi 独自メタデータ。元ファイルは改変しない）
  target_type        repository | session
  target_id
  pinned / tags[] / note

ToolProfile
  tool / enabled / executable_path / version / data_dir / last_scanned_at
```

**全文検索インデックス**は `Message.content` に対する SQLite FTS5 を想定する（NFR-1.3）。

## 7. 技術方針（参考・非拘束）

要件ではなく実装への推奨。設計フェーズで再評価してよい。

### 7.1 アプリケーションフレームワーク

> **Q-1 で内蔵ターミナル（FR-7.8）が MVP に入ったため、この節は再評価済み。**

| 候補 | 長所 | 短所 | 評価 |
| --- | --- | --- | --- |
| **Tauri 2**（Rust + Web UI） | 起動が速く省メモリ（NFR-1.1, NFR-1.7 に有利）。Rust で JSONL のストリーミングパースとファイル監視を高効率に実装できる。配布サイズが小さい。署名／公証／自動更新の仕組みを内蔵。OSS 化（NFR-4b）でもライセンス上の摩擦が少ない | Rust の学習コスト。**内蔵ターミナルは Electron より手数が多い**: PTY を Rust 側（`portable-pty` 等、Windows は ConPTY）で持ち、出力バイト列を IPC で WebView へ流す実装が必要 | **推奨（据え置き）** |
| Electron | `node-pty` + `xterm.js` が内蔵ターミナルの定番構成で、実装リスクが最も低い | メモリ・配布サイズ・起動時間で不利。**NFR-1.1（起動 2 秒）と NFR-1.7（400MB）の達成が難しく、ターミナルを複数開けばさらに悪化する**。GB 級 JSONL のパース性能でも不利 | 次点 |
| .NET MAUI / Avalonia | ネイティブ | macOS 側の成熟度と UI 表現力に懸念。ターミナル部品も自前 | 非推奨 |

**判断**: 内蔵ターミナルは Electron の方が容易だが、それは**このアプリの主要な負荷ではない**。本質的な負荷は 1 万セッション・GB 級 JSONL のパースと全文検索であり、そこは Rust が明確に有利で、性能要件（NFR-1）もそちらに引かれて設定されている。ターミナルは「難しいが解ける既知の問題」である一方、Electron でのメモリ・起動時間の不利は**設計で解消できない**。よって **Tauri 2 を維持**する。

**推奨構成**: Tauri 2 + Rust コア + React/TypeScript UI + SQLite（FTS5、`rusqlite`）+ `notify` クレートによるファイル監視（Windows: `ReadDirectoryChangesW` / macOS: `FSEvents`、デバウンス付き）+ PTY（`portable-pty` 相当）と `xterm.js`。

**ただし M0 で必ず技術検証（スパイク）を行うこと**（R-10）:

1. Windows（ConPTY）と macOS の双方で対話型 CLI が正常に動くか — 特に **TUI を持つ CLI**（Codex / Claude Code はいずれも画面制御を行う）でのカーソル制御・リサイズ・カラー
2. 大量出力時の IPC スループット。Tauri v2 のストリーミング機構（`Channel` 等）で描画が破綻しないか
3. ターミナルを 3 つ開いた状態でのメモリ実測（NFR-1.7 の 400MB に収まるか）

この 3 点が満たせない場合に限り Electron への切り替えを再検討する。判断は M0 の終了時点で行い、M1 以降には持ち越さない。

### 7.2 アダプタ設計（NFR-5.1）

各ツールを次のインタフェースで抽象化する。

```
trait ToolAdapter {
    fn id(&self) -> ToolId;
    fn detect(&self) -> Result<ToolProfile>;            // FR-1
    fn data_roots(&self, profile: &ToolProfile) -> Vec<PathBuf>;
    fn discover(&self, root: &Path) -> Result<Vec<SessionRef>>;   // FR-2.1
    fn parse(&self, r: &SessionRef) -> Result<ParsedSession>;     // FR-2.x
    fn watch_targets(&self, root: &Path) -> Vec<WatchSpec>;       // FR-2.4
    fn resume_command(&self, s: &Session) -> Result<Command>;     // FR-7.2
    fn new_session_command(&self, repo: &Repository) -> Result<Command>; // FR-7.7
}
```

**OpenCode については、ファイル直読みではなくローカル HTTP API（`opencode serve` + OpenAPI/SDK）を第一の情報源とする**ことを推奨する。
OpenCode はストレージ実装（JSON ファイル → SQLite）が変遷しており、API の方が安定インタフェースである。API が利用できない場合にファイル直読みへフォールバックする二段構えとする。

## 9. MVP 完了条件（Definition of Done）

以下をすべて満たしたとき MVP を完了とする。

1. Windows 11 と macOS の双方で、署名の有無を問わずインストールして起動できる
2. 3 ツール（Codex CLI / Claude Code / OpenCode）がインストール済みの環境で、すべてのセッションが検出・一覧できる
3. 全セッションがリポジトリ単位で正しくグルーピングされる。worktree・移動済みリポジトリ・リポジトリ外セッションが FR-3 の規定どおりに扱われる
4. 任意のセッションの会話内容が読める（ツール呼び出しと結果を含む）
5. 横断全文検索が動作し、NFR-1.3 の性能目標を満たす
6. 任意のセッションを「再開」でき、正しい cwd で正しいコマンドが起動する（3 ツールすべて）
7. **内蔵ターミナル**から 3 ツールすべてのセッションを再開・新規開始でき、対話が成立する（Windows / macOS 双方で検証）
8. セッションの削除が、有効化・対象列挙・確認・ゴミ箱移動の順で安全に行われ、実行中セッションは削除できない
9. 元のセッションファイルが、削除操作を除いて一切改変されていないことを検証できる（実行前後のハッシュ比較テスト）
10. 外部ネットワーク通信が発生しないことを検証できる（ネットワーク遮断環境での全機能動作テスト）
11. 破損ファイル・未知形式ファイルを混入させてもクラッシュしない（NFR-2.2 のテスト）
12. `LICENSE` / `SECURITY.md` / `CONTRIBUTING.md` が揃い、依存ライセンス検査とゴールデンファイルの秘匿情報チェックが CI で動いている（NFR-4b）

## 13. 用語

| 用語 | 定義 |
| --- | --- |
| セッション | 1 つのエージェント CLI との一連の対話。会話メッセージとツール実行の履歴を含む |
| ネイティブセッション ID | 各 CLI が内部で採番するセッション識別子。再開コマンドに用いる |
| リポジトリ | git のワーキングツリーのルート。本アプリのグルーピングの基本単位 |
| worktree | `git worktree` により作成された、同一リポジトリの別チェックアウト |
| アダプタ | 特定の CLI ツールに対応する、検出・探索・解析・起動の実装単位 |
| インデックス | Mochi が構築する正規化済みローカル DB。元ファイルから再生成可能なキャッシュ |
| トランスクリプト | セッションの会話記録そのもの（JSONL ファイル等） |
